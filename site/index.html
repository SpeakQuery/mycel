Why would you use it?

Your tools shouldn't eat your context.

In clients that send every tool definition on every turn, each MCP server adds its full tool list. Add servers and the stack climbs until it crowds out your real work. Drag the slider. Then flip the switch.

Measured with real open-source servers up to 8. Beyond 8 the stack is an estimate.

  • −93.5%

    −93.5% context with 8 servers

    17.9k tokens of tool definitions per turn become 1.16k (reproducible: examples/field-test (CI runs it on Ubuntu and Windows)). The model searches the catalog and loads a schema only when it needs one.

  • 17 calls, 1 trip

    17 calls, 1 round trip

    With Code Mode the model writes one short script and a sandbox runs the calls. Only the result comes back. 17 tool calls in 1 model round trip. A client that makes one tool call per turn needs 17 turns; an efficient direct path using batch tools (read_multiple_files) needs about 3. Code Mode assumes the model writes a working script first time; not yet measured with a live model. Gateway overhead: about +0.4 ms on a Mac, +1 ms in CI (Ubuntu, Windows); median of 15 local calls.

  • Blocked

    Untrusted web page can't write files without approval

    Content from untrusted servers is tainted. A tainted call that writes, sends or deletes waits for a human. Mycel reduces the risk of prompt injection; it doesn't solve it.

Same tools. A fraction of the context.

More room for your actual work, fewer slow turns, and a trust layer in between. Measured with mycel bench: the same catalog of 12 servers, called directly over MCP and through Mycel.

Who it's for

Eleven sectors, each with an honest status.

The evidence is a mock or scripted setup with a small n, not a field result. Local, single-user, read-heavy use is the recommended pilot; paid jobs with automatic fallback are not.

  • 🔬 Researchers and data analysts

    MEASURED (with caveat)

    Big CSV/SQL results become a ref plus a digest; a Code Mode scan found what a text search missed.

    Scenario and evidence

    Pain: big CSV/SQL results and PDFs flowing through the prompt.

    1. In a 20,000-row dataset with two exceptions, a text search on the ref found one and missed the other. A Code Mode numeric scan over the ref found both.
    2. The model's first report omitted both until it was asked to verify against the file.
    3. Lesson: verify against the full data; digests don't guarantee every exception is seen.
    4. Earlier single run: rare row in a 20,000-row CSV, cache off: direct 12 turns / 34.5 s vs Mycel 4 turns / 6.6 s.

  • 🧑‍💻 Developers with many MCP servers

    PARTIAL

    8 servers, 80 tools: 17.9k → 1.16k definition tokens where the client sends them all.

    Scenario and evidence

    Pain: git, filesystem, Playwright, a database and docs (e.g. context7) in a client or framework that sends every definition up front.

    1. 8 servers, 80 tools: 17.9k → 1.16k definition tokens (chars/4).
    2. A scripted fix flow (git + browser + db) works; a model-written patch failed.
    3. Turkish search put the right tool in the top 3 in 0/5 queries; English is much better.
    4. Not for you if you run 1–2 small servers, or use Claude Code/Cursor only for definition savings.

  • 📣 AI editors and content/marketing teams

    PARTIAL

    Find designs, read assets by ref; publish or send needs approval under the example policy.

    Scenario and evidence

    Pain: designs, docs and brand assets across many tools, and agents that can publish or send unseen.

    1. Servers: Canva, docs, storage. The agent finds designs with mycel_search and reads assets by ref.
    2. With the example policy, publish or send (an external effect) needs approval, inline or mycel approve.
    3. In the mock publish test, approval was needed only because of that policy; the default policy allows a clean external call.
    4. The model added unsourced claims to the text.

  • 🎬 Video / voice producers

    PARTIAL (pilot)

    Refs between agents, budget caps and jobs for slow renders; automatic paid fallback not yet recommended.

    Scenario and evidence

    Pain: base64 media in the prompt, renders that time out mid-call, every agent holding every key, runaway spend.

    1. A 5-agent mock pipeline worked: per-role tokens, refs passed between agents, the budget cap rejected the second, sequential request, and the final file had video and audio (5.000 s).
    2. Real Higgsfield (n=1, 2026-11-27): Mycel was the only path to the real Higgsfield MCP (remote URL + OAuth, 241 tools). Tool definitions for 270 tools: ~155k → ~962 tokens (−99.4%, estimated). Polling six renders with mycel call from a shell script cost 0 model tokens per check vs ~85k for a subagent check (measured). The videos were submitted by another agent directly, so generation through Mycel is not measured yet. Field report.
    3. Generating through Mycel vs direct, and Canva, were not measured.
    4. Not yet recommended: automatic fallback across paid providers. After a paid request with an unknown outcome Mycel never falls back to another provider. It re-sends to the same tool only if that tool is idempotent, has idempotencyKeyArg (the same key is re-sent) and has retries left; otherwise it marks the job unknown and sends nothing more. The estimated charge is recorded once per (tool, key). A request is treated as rejected, and so may fall back, only when it is known not to have been accepted (connection refused before dispatch, or an error from a tool whose contract sets errorsAreRejections: true). After a restart, a job whose last request went to a paid tool resumes only if that tool is idempotent and has idempotencyKeyArg; otherwise it is marked interrupted and the estimate is charged once. This is not exactly-once: the provider must deduplicate (Mycel can pass a stable per-job key via idempotencyKeyArg). Attempts that the job queue sends are recorded in the job's dispatches; retries inside a single call's transport loop are not. On success the budget records the tool's declared costUsd for the call (the contract amount, not a provider invoice); otherwise it records the estimate, and charged in dispatches only means an estimate was written (a definite rejection writes none). A manual mycel_job retry of a job whose last paid dispatch is unresolved deliberately reuses the same idempotency key, so a deduplicating provider can collapse it into one receipt; per (tool, key) only one estimate is kept, and a later success replaces it with the actual charge (never both). Dispatches without a key are each charged. Reconcile paid jobs with the provider statement whatever their final status, not only unknown and interrupted (no reconcile tool yet; jobs recorded by 0.1.3 or earlier are not re-settled on upgrade). Estimates can exceed what the provider charged, and the dashboard spend mixes estimated and confirmed charges.

  • 🎧 Customer-support agents

    PARTIAL

    Untrusted customer text can’t trigger a refund or an email without approval.

    Scenario, pilot metric, not a fit

    Who: Support teams running an agent over tickets, orders and a knowledge base.

    Typical MCP servers: ticketing/helpdesk, CRM, knowledge base, email, payments/refunds.

    Pain: Ticket histories are long, and the customer’s text is untrusted input sitting next to tools that can refund or send mail.

    Evidence (independent review, mock services, 3 runs each): scripted runs 3/3 produced the right draft; a 1,800-line ticket history stayed as a ref; all 6 injected refund/email attempts stopped for approval (0 unapproved side effects, 0 unnecessary approvals). With a small local model (Qwen3-4B) 0/3 reached the right end state (wrong order id, no draft): a model limit, no Mycel-specific failure. Note: approval for trusted external actions (email, share, upload) requires an explicit { match: { effect: external }, action: approve } rule; the default policy allows them.

    1. Mark the ticketing and email servers trust: untrusted; the long ticket history comes back as a ref plus a digest instead of thousands of lines in the prompt.
    2. The agent searches the knowledge base with mycel_search and greps the ref for the order id and earlier promises.
    3. Its draft reply and refund call carry taint from the customer text, so the default policy (tainted + side-effect → approve) stops them until an agent supervisor approves inline or with mycel approve.
    4. Refund and send calls are external/destructive contracts; add a per-day budget if the payments tool declares costUsd.
    5. Every search, describe, call, run, ref, job and approval decision appears as a span in the flight recorder for later review.

    Measure in a pilot: Share of tickets where the model needed the full history in the prompt, approvals raised vs. approvals that were correct, and any tainted write that got through (target: zero).

    Not a fit: A hosted, multi-tenant support desk serving many customers from one gateway: Mycel is local and single-user today.

  • 🛒 E-commerce operations

    PARTIAL

    Bulk catalog and price changes in one script, with approval before anything goes live.

    Scenario, pilot metric, not a fit

    Who: Shop operators and catalog/merchandising teams.

    Typical MCP servers: product catalog (CSV or database), storefront/admin API, image generation or editing, file storage.

    Pain: Catalogs run to thousands of rows, price updates are repetitive, and a wrong publish is visible to customers.

    Evidence (independent review, mock services, 3 runs each): scripted runs 3/3 corrected the three under-cost prices among 24,000 products, 0 false positives, and every price list waited for publish approval (explicit external→approve rule); the catalog never entered the model context. A small local model (Qwen3-4B) 0/3 (could not compare prices over the CSV, no draft). Note: approval for trusted external actions (publish, upload, send) requires an explicit `{ match: { effect: external }, action: approve }` rule; the default policy allows them.

    1. Export the catalog; it becomes a ref with a table digest (columns, row count, sample) rather than rows in the prompt.
    2. The model writes one Code Mode script that loops over the ref, computes new prices and prepares the update payloads in a single round trip.
    3. Image generation or editing calls run as jobs with progress, cancel and retry; results are refs passed on to the storefront tool.
    4. The publish/price-update tool is an external effect: the policy requires approval, bound to the exact arguments.
    5. Declare costUsd on image tools and set a per-day cap so a loop can’t quietly spend.

    Measure in a pilot: Rows changed per approval, wrong prices caught at the approval step, turns and time for a 1,000-row price change vs. direct tools.

    Not a fit: A handful of products or one-off edits: direct tools are simpler. Paid image jobs with automatic fallback are not yet recommended (see the paid-jobs note in the README).

  • ⚖️ Legal / document review

    PARTIAL

    Long contracts stay on disk as refs; clauses are found with grep and nothing leaves without approval.

    Scenario, pilot metric, not a fit

    Who: Lawyers, paralegals and in-house teams reviewing documents on their own machine.

    Typical MCP servers: filesystem or document store, PDF/text extraction, email or sharing tools.

    Pain: Contracts and PDFs are long, versions differ in small ways, and confidential text must not be sent anywhere by accident.

    Evidence (independent review, mock services, 3 runs each): scripted runs 3/3 found all 3 changed clauses across two 36-page versions, 0 missed, 0 invented; with the explicit approval rule all 9 send attempts stopped. Small local model 0/3 (answered without opening the documents). Note: approval for trusted external actions (email, share, upload) requires an explicit { match: { effect: external }, action: approve } rule; the default policy allows them.

    1. Contracts and exhibits are read as refs; the model sees an outline digest instead of hundreds of pages.
    2. It greps the refs for clauses (indemnity, termination, governing law) and reads only the matching lines.
    3. To compare two versions it runs a Code Mode script over both refs and returns only the differing clauses.
    4. Any email, share or upload tool is an external effect and needs approval before anything leaves the machine.
    5. The flight recorder keeps a local record of which documents were read and what was sent.

    Measure in a pilot: Clauses found by grep vs. a manual read of the same documents, missed differences in version comparison, and tokens used per document.

    Not a fit: Shared or multi-user matter workspaces, or anything that needs client-level access control: Mycel is single-user and local. It is a reading aid, not legal advice, and it does not guarantee that a search sees every clause: verify against the full text.

  • 📊 Finance & accounting reporting

    PARTIAL

    Big ledger exports stay out of the prompt; paid data lookups are capped and every call is recorded.

    Scenario, pilot metric, not a fit

    Who: Finance analysts and accountants preparing reports and reconciliations.

    Typical MCP servers: ledger/ERP export, spreadsheet or database, paid market or reference-data APIs, file storage.

    Pain: Ledger exports and spreadsheets are huge, reconciliation is many small steps, and paid data APIs can be called in a loop.

    Evidence (mock services): scripted runs 3/3 found all three issues in 32,000 ledger rows; in every run the two mock provider receipts matched Mycel's ledger; a third call that would exceed the $0.10 budget cap was refused; the flight recorder had 18 of 18 tool calls. Small local model 0/3 (did not call the ledger/FX tools).

    1. The ledger export and the bank statement become refs with table digests.
    2. A Code Mode script matches the two over the refs and returns only unmatched lines, one round trip instead of many.
    3. Paid data APIs get costUsd in their contracts and a per-task or per-day budget cap checked on each call.
    4. Writes to the accounting system are write/external and go through approval.
    5. The flight recorder gives a timed audit trail of what ran; money is read from the budget ledger, which holds estimates and declared costs, not provider invoices.

    Measure in a pilot: Reconciliation turns and time vs. direct tools, unmatched items missed vs. a manual check, and budget-ledger spend vs. the provider statement.

    Not a fit: Anything needing a regulated, tamper-proof audit log: the flight recorder is local JSONL, not a certified control. Not for multi-user ledgers.

  • 🛠️ Data engineering / ETL quality

    PARTIAL

    Row-level checks run in Code Mode over refs, so mislabeled or unflagged records are found without reading the table.

    Scenario, pilot metric, not a fit

    Who: Data engineers and data-quality owners checking pipeline outputs.

    Typical MCP servers: SQL/warehouse query tool, filesystem, object storage, ticketing for reporting issues.

    Pain: Result sets have thousands of rows and the bad ones are rare; a sample can miss them.

    Evidence (independent review, mock services, 3 runs each): scripted runs 3/3 found all 3 issues in 50,001 rows, 0 false positives, both direct and through Mycel. Context size for the same 2-turn task: 583,980 tokens direct vs 602 through Mycel (requests + responses, chars/4). Local median latency 37.7 ms direct vs 319.3 ms Mycel. Small local model 0/3 in both arms.

    Closest evidence: The closest evidence is the measured CSV case: in a 20,000-row dataset with two planted exceptions, a text search on the ref found one and a Code Mode numeric scan found both; the first report omitted both until asked to verify. This sector's own scripted runs are in the evidence line above.

    1. A SQL result comes back as a ref plus a digest (columns, row count, sample).
    2. A text search on the ref is a quick first pass, but it can miss rows.
    3. A Code Mode script scans every row of the ref against the rule (for example label vs. value, missing flag) and returns only violations.
    4. The model reports counts and ids, and is asked to verify against the full file before concluding.
    5. Writing fixes back or opening tickets goes through policy and approval.

    Measure in a pilot: Planted exceptions found by the text search vs. the Code Mode scan, and the model’s first report vs. its verified report.

    Not a fit: Streaming or very large tables that don’t fit as a single ref; 1–2 small servers where Mycel only adds context.

  • 📱 Agencies & social-media teams

    MEASURED (mock pilot)

    Each agent gets its own narrowed token, so a posting agent can’t touch billing, and posts need approval.

    Scenario, pilot metric, not a fit

    Who: Agencies and in-house social teams running several agents over many client accounts.

    Typical MCP servers: Canva or other design tools, scheduling/publishing, analytics, ad or billing tools, storage.

    Pain: Many client tools, many agents, and one over-privileged key means a posting agent could reach billing.

    Evidence (mock pilot): scripted 3/3 and a real local model (Qwen3-4B) 3/3: with a posting-only capability token, billing calls were refused for every client, the analytics report travelled as a ref, and posting waited for approval (3 approval ids matched the queue; 0 unapproved posts). Measured with mock services; real platform APIs not tested.

    1. A human mints a capability token per role with mycel token mint (and agents can narrow it with mycel token attenuate): the design agent gets design tools, the posting agent gets scheduling only, each with a lower effect ceiling and a small budget.
    2. Designs are found with mycel_search and passed between agents as refs.
    3. Posting and scheduling are external effects; the policy requires approval before anything is published.
    4. Tokens expire and can only be narrowed further, never widened.
    5. The flight recorder shows which agent called which tool, and the budget shows spend per task.

    Measure in a pilot: Calls a token correctly refused (billing from the posting agent), approvals needed per campaign, and spend per client.

    Not a fit: Hosting many clients’ credentials for many users on one shared gateway: Mycel is single-user and local today. One or two tools: no need.

  • 🎨 UI/UX & product designers

    MEASURED (n=1, real service)

    Generated screens and HTML stay out of the model context and are saved by ref, not re-typed.

    Scenario, pilot metric, not a fit

    Who: Product designers, UI/UX designers and design-minded developers using AI design tools from an agent.

    Typical MCP servers: Google Stitch or another design-generation service, a filesystem server, design-system and asset storage.

    Pain: Each generated screen returns its full HTML and metadata into the prompt, and saving a file means the model re-types it into a write tool.

    Evidence (real Google Stitch MCP, claude-haiku-5-5, n=1 per arm, 2026-11-27): 6 mobile screens, then the checkout HTML saved to payment.html. The problem

MCP made tools pluggable. It didn't make them cheap, fast or safe.

Connect a dozen servers and your agent pays for it on every turn. Eight pains we kept hitting:

  1. Context bloat

    Every server dumps its full tool schemas up front. Thirty servers cost tens of thousands of tokens before the first word.

  2. Everything flows through the model

    Moving 10k rows from tool A to tool B means 10k rows in the context window.

  3. Round-trip storms

    A 10-step task becomes 10 inference turns, each one slow and billed.

  4. Security bolted on

    Tool output can smuggle instructions, descriptions can change silently (rug pulls), and API keys sit in prompts.

  5. Tools don't describe their cost

    No latency, no price, no hint whether a call can be undone.

  6. Long-running work has no home

    Video, render and training calls simply time out.

  7. Agents can't safely delegate

    Sub-agents inherit full credentials, with no way to narrow them.

  8. No black box

    Nobody can see what an agent did, or why.

Do you need Mycel?

The more MCP servers you use, the more it pays off.

Measured with 8 real open-source MCP servers (filesystem, git, fetch, time, memory, Playwright and more), added one at a time. Mycel's own footprint stays flat at about 1.2-1.3k tokens. Direct MCP grows with every server, and a client that sends every definition makes the model re-read it on every turn. Reproducible: examples/field-test (CI runs it on Ubuntu and Windows).

Use it if

  • You use 4+ MCP servers, or one big one (Playwright, GitHub, Notion: 20–90 tools each).
  • Your tools return big results: files, tables, logs, page snapshots, images, video. A 20,000-row CSV is 131k tokens direct and 187 through Mycel.
  • Your agent works in many small steps. Code Mode turns 17 tool calls into 1 round trip.
  • Your agent reads untrusted content (web, email, tickets) and can also write, send or delete.
  • You need approvals, budgets, an audit trail, or other agents (A2A) calling your tools.

Skip it if

  • You run 1–2 small servers and only make short, read-only calls. Your client is fine on its own.
  • You don't need a safety layer, refs or Code Mode. Mycel uses more context there: on a 4-tool catalog (time + fetch) a real tokenizer (o200k) counts 902 tokens direct vs 1,424 through Mycel, about 58% more. Don't use it for 1–2 small servers.
  • Your client matters too. Claude Code already loads tool definitions on demand, so there Mycel is mainly for Code Mode, refs for big results, safety and A2A. Cursor (recent versions, "dynamic context discovery") also loads tools on demand. Other clients and frameworks may send definitions up front: check your client. Definition savings in on-demand clients are smaller and not yet measured.

Run it on your machine: examples/field-test in the repo (10 checks, macOS / Linux / Windows). Per-call overhead: about +0.4 ms on a Mac, +1 ms in CI (Ubuntu, Windows); median of 15 local calls. Search quality: field test top-3 is 15/16 (CI and local), top-1 12/16 in the latest runs (the old 10/16 was an earlier run). On an independent 32-pair EN/TR set, raw BM25 gets the right tool in the top 3 for 20/32 English and 3/32 Turkish queries; with a small model (Haiku) choosing and allowed one query rewrite, 27/32 English and 25/32 Turkish are correct. The offline index is English-only. The table above uses the chars/4 estimator, which understates Mycel's overhead at 1–2 servers.

Architecture

A gateway on the way in, a mesh on the way out.

Clients speak plain MCP to Mycel. Remote agents speak A2A. Behind it, every upstream server and agent is reached through one trust layer and one recorder.

Advanced: configure policies, budgets and Code Mode

1 Declare servers, policy and budgets

One file. Secrets stay placeholders; servers imported over HTTP are marked untrusted (hand-configured servers default to trusted unless you set trust: untrusted); large results become refs.

mycel.yaml
servers:
  github: { command: npx, args: ["-y", "@modelcontextprotocol/server-github"], env: { GITHUB_TOKEN: "{{secret:GITHUB_TOKEN}}" } }
  studio: { url: "https://studio.example.com/mcp", trust: untrusted }
policy:
  - match: { tool: "github.*delete*" }
    action: deny
  - match: { effect: destructive }
    action: approve
  - match: { effect: external }
    action: approve
budget: { perTaskUsd: 5, perDayUsd: 50 }
refs: { inlineLimitBytes: 8000 }

2 The model writes one script, not ten turns

Via mycel_run, the script runs in a QuickJS sandbox. Intermediate data never enters the context; only the return value does.

code mode · sandboxed JS
const issues = await tools.call("github.list_issues", { repo: "acme/web", state: "open" });
const stale = issues.filter(i => daysSince(i.updated_at) > 30);
for (const i of stale) await tools.call("github.add_label", { repo: "acme/web", issue: i.number, label: "stale" });
return { labelled: stale.length };

3 Policy decides before anything irreversible

Rules match by effect or tool glob. With this example policy a destructive or external call pauses for approval; a forbidden one never reaches the server.

mycel.yaml · policy
policy:
  # reads flow freely
  - match: { effect: read }
    action: allow
  # anything destructive waits for a human
  - match: { effect: destructive }
    action: approve
  # and some things are simply off-limits
  - match: { tool: "github.*delete*" }
    action: deny
  # publish / send needs a human (the default policy allows a clean external call)
  - match: { effect: external }
    action: approve

FAQ

Questions, answered straight.

Is Mycel a new protocol?

No. Mycel is a drop-in layer. To your client it is a standard MCP server; to other agents it is a standard A2A agent. Your existing MCP servers and clients keep working without changes for tools; resources and prompts parity is not yet verified.

I only use one or two MCP servers. Do I need it?

Probably not, and not for context savings: with 1–2 small servers Mycel uses more context (about 58% more on a 4-tool catalog with a real tokenizer), so don't use it for that. It starts paying off around 4 servers, or with one large server like Playwright or GitHub. With fewer, you'd use it for Code Mode, refs for big results, the safety layer or A2A. See "Do you need Mycel?" above.

Does it run on Windows?

Yes. Mycel is plain Node.js and is tested on Linux, macOS and Windows in CI. Install with npx -y @speakquery/mycel setup. The servers you put behind it bring their own needs; Python servers, for example, need uv.

Does it work with Canva, Notion and other servers that need a sign-in?

Yes. Run mycel login canva once, after setup. Mycel follows the MCP authorization spec (OAuth with PKCE), stores the tokens only on your machine and refreshes them automatically.

Does it send my data anywhere?

No. Mycel is local-first: no account, no cloud, no telemetry. Traces stay on your machine as JSONL unless you configure your own OpenTelemetry endpoint. The only network traffic is to the servers, agents and models you configure.

Does it solve prompt injection?

No, and we'd be wary of anyone who says they do. Mycel reduces and exposes the risk: untrusted content is tainted, destructive actions with tainted inputs require approval, secrets referenced as {{secret:NAME}} are injected by Mycel and scrubbed from outputs, errors and traces (a server that echoes a secret in an unusual encoding could still leak it), tool manifests are pinned, and tool calls that run through Mycel's call path are recorded (not mycel_job status/wait reads, unknown tools or invalid refs). That makes attacks harder and visible, not impossible.

Which clients does it work with?

Any MCP client: Claude Desktop, Claude Code, Cursor, VS Code, Windsurf, ChatGPT connectors and local LLM hosts, over stdio or Streamable HTTP.

What does it cost?

Nothing. Mycel is open source under the Apache-2.0 license. Budget caps in the config are checked per call; for a job the check runs once, when it is queued, against the primary tool's price, so fallbacks and manual retries get no separate pre-dispatch check and nothing is reserved: concurrent paid jobs can exceed a cap at the provider.
